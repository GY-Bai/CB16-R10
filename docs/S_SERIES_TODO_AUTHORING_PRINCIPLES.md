# S 系列 TODO 撰写角色原则

日期：2026-09-13。适用角色：把最高理念与科学计划转成 S 系列可执行任务的撰写者、维护者和审阅者。用户现已指定 Astra 文档、Sol TODO、DS Flash 代码的分工及逐层监督，详见 [三层对齐与审核协议](ROLES_AND_REVIEW_PROTOCOL.md)。名称不构成能力证明或额外运行权限。本文属于文档与任务设计规范，不是新 science authority，不修改已冻结实验或 receipt。

当前实例见 [S0/S1 可执行性审阅](reviews/S0_S1_EXECUTABILITY_REVIEW_2026-09-13.md)。当前 task numbering 仍沿用 [S0/S1 总控](R11_POST_CC_S0_S1_TODO.md)，不得据本文另拆一套重复任务。

## 1. 角色目标：交付一个别人能执行并判定的任务

TODO 作者负责把“希望学会什么”变成明确的输入、已有实现、需要补齐的行为、依赖、运行方式和判定。完成标准是另一个执行者无需重新猜科学问题，就能开展开发，并在约定条件下产出相同含义的 verdict。

用户已经确定：Market + Account + 必要因果历史形成决策闭环；允许反复练习；完整保留成功失败；以完整算术期望收益为目标；冻结器官、训练 Brain；双基准并列诊断、相对改善可晋升沙盒冠军。作者不得重新悬置这些原则，也不得为获得 PASS 偷换为保守风险目标、幸存者排名或市场预测题。

作者可以在授权内选择、论证和预登记常规算法/工程参数；涉及目标改变、权限扩大或与冻结合同实质冲突时，先写出具体差异与后继方案。不能把“待实现”变成需要 owner 再授权；也不能用“继续执行”掩盖没有定义的科学判据。

## 2. SW-01：先核实实际断点，再写任务

每次修订至少核对：当前 main SHA、实际工作分支及相对基线净差异、相关 spec/receipt 与运行结果。精确区分：

- 规划基线：从哪一版理念/计划拆解。
- 合格实现 SHA：哪一版代码获得哪种资格。
- 带 receipt 的交接 SHA：执行者应从哪里取得完整交接材料。
- 当前工作 head：任务实际推进到哪里。

这些身份可以不同，名称和机器字段必须一致。不能让正文要求从交接 head 开工、run spec 却被解释为退回不含 receipt 的代码 head。工作分支前进不等于冻结基线被替换；提交数量也不等于实现进度。

状态必须来自证据：`AUTHORIZED/ACTIVE` 表示可开展，`IMPLEMENTED` 表示代码存在，`QUALIFIED` 表示指定资格成立。完成阶段在导航中关闭，原任务正文标为历史要求；不要一处 PASS、一处 OPEN。

## 3. SW-02：每项任务至少形成一个完整的执行约定

以下可写成短段落，不要求每项机械填长表：

| 必需内容 | 写到什么程度 |
|---|---|
| 问题与完成后的行为 | 说明改变哪一种可观察能力；避免“完善”“加强”作为唯一目标 |
| 输入和已有代码 | 精确 artifact/符号/合同及来源；哪些已具备、哪些缺失 |
| 修改范围 | 复用、适配、新增或显式替代；建议文件名不是强制一任务一文件 |
| 依赖与阶段出口 | 能从哪个已存在产物开始；完成后交给谁；不形成循环依赖 |
| 验收输入与预期输出 | 正常例子、相关反例、比较方式和判据；“加测试”不算验收定义 |
| 执行与资源 | 已存在命令，或由哪项任务提供命令；必要设备、时间/内存/存储预算 |
| 代码审核责任 | Sol 审查 DS 实际 SHA；指出公式、比较分支、边界和判分的高风险位置及独立验收依据 |
| 交付与证据 | 代码、结果、来源和 hash；只声称实际验证到的能力 |
| 未完成与异常处理 | 下一步是什么；什么是任务未做完、真正阻塞、有效科学 FAIL |

新命令在实现前不存在是正常的，应标注 producer task；不能把不存在的命令写成当前已可运行入口，也不能要求先运行它才准创建实现。

## 4. SW-03：区分“可开始开发”和“可开始资格运行”

**可开始开发**：目标、输入合同、作用范围与第一步清楚。后续 store、learner、runner 不存在，正是实现任务，不能因此整体停工。

**可开始资格运行**：具体环境/任务参数、观察与动作、奖励/边界、模型/优化器、种子、采样/更新、预算、评价与 gate 已完整且自洽地解析成一个 manifest；必要实现和局部验收完成。

`FROZEN` 字符串、文件 hash、任务 ID 列表只能证明某份内容固定，不能证明内容足够执行。任务可保留后续待实现细节，但必须明确“谁在何时补齐、允许补什么、需要哪种版本化”。

这两个条件是撰写质量标准，不新增一套审批会或重跑全部历史资格。缺少正式运行信息时，已明确的组件开发、解析式 oracle 和完整性检查继续进行。

## 5. SW-04：把科学任务写成可生成、可评分的对象

科学任务的发布版本应覆盖：

- 环境转移/结果概率或确定性生成规则、参数域、初始账户与可达性。
- 每个输入字段、顺序、维度、单位和因果归一化；禁止 oracle/未来答案进入 Actor。
- 名义动作空间及风险区域，如何通过实际执行改变账户；奖励从哪里来。
- episode/phase/chunk/decision 的长度，真实终止、计算截断和 bootstrap 的不同含义。
- oracle 的计算方法、可见信息及政策类；如何处理连续风险最优值只可逼近的情形。
- 初始政策、最终政策、评价样本/积分方法、聚合、误差容忍和最终 success predicate。

“延迟后果”“高风险高期望”“A→B→A”是研究问题的名称，不是完整环境定义。“明显改善”“materially outperform”“where applicable”不能独自成为最终机器判据；适用条件、量纲、阈值、分母必须在看学习结果前确定。

不要求所有任务都用同一个分数。若用 oracle gap，明确计算式、方向、零/负分母、不确定 oracle 的处理；若某任务评价 retention/relearning，明确测试发生在返回 A 立即、还是经过多少次再学习之后。两者证明不同能力。

## 6. SW-05：先证明题目可由规定输入和模型完成

已知答案必须受同样的信息和动作约束。全知 oracle 的最好收益不一定是冻结无记忆 Brain 可达到的目标。

例如 A/B 使用完全相同观察却要求不同动作，而 Actor 无记忆又禁止任何可辨识信息，则不应把“立即识别返回 A”当可达要求。可以设计自然可辨识的因果观察或明确的再学习协议，但不得看到结果后临时塞任务 ID、phase 标记或手工规则。

账户消融须检查 Market、Execution、历史状态等其他通道是否仍泄露同一账户答案。oracle、环境可达性与输入充分性的解析验证可以先做；不必等全部 learner 完成才发现题目不可解。

S1 小模型失败不能自动判定整个项目不可能；同样也不能未经版本变更扩大模型来补救冻结任务。

## 7. SW-06：正控、负控和完整性攻击分别定义

| 控制类型 | 应检验的内容 | 常见错误 |
|---|---|---|
| 已知可学正控 | 完整学习链能利用已知信号 | 把预计算收益/正确动作直接输入 learner，再称来自经历的学习 |
| 无信号/零奖励对照 | 预登记统计下没有系统性学习证据 | 无条件要求所有随机种子绝不偶然达标，或用零 oracle gap 作分母 |
| 打乱信用对照 | 指定操作确实破坏所检验的条件关联，保留需要匹配的其他因素 | 仅调用 shuffle，却没证明它破坏了该任务的信号 |
| 随机/不可预测目标 | 在明确不可预测的评价条件下不能系统性预测 | 要求模型连反复出现的有限随机标签也不能背会，违背复习任务含义 |
| 数据/概率破坏攻击 | 改 hash、伪造 log_mu 或替换名义动作被拒绝 | 把拒绝损坏文件当作模型学会了交易 |

控制必须写明改了什么、训练用什么、评价用什么、预期关系及随机误报容忍。随机目标若反复训练且原样评价，可能被记忆；这不自动意味着泄漏。禁止从负控名称直接推导数学结论。

## 8. SW-07：冻结科学含义，允许受控实现细化

至少区分：任务族/语义合同、具体实验参数、实现/运行 manifest、结果/receipt。各对象绑定自己的 hash 与父身份，不把四者混成一份名为 run spec 的模板。

- 只补文件路径、设备、代码 hash 等绑定信息：在既有合同内形成运行 manifest。
- 对原来未数值化的生成器、评价、对照作具体化：发布可审阅的执行补充，列出兼容性和新的 hash；不能假称这些数值早已冻结。
- 改已有科学参数、奖励、任务难度、阈值、模型或种子：新版本，保留原来版本与已见结果；不得覆盖冻结文件。

“第一次看到结果”的边界要涵盖实际被用于选择的开发试验，不仅是名叫 qualification 的那一次。可用独立开发 fixture 与解析检查完善工程；已用同一任务学习结果调参，则记录探索身份，再定义合规后继确认。不得通过改 run 名把事后选择洗成预注册。

原 receipt 的 PASS 只覆盖当时实际检查内容。发现资格检查只验证字段存在而未验证判据充分性，应补后继证据并收窄解释，不删除原 receipt，也不要求执行者忽略具体缺口。

## 9. SW-08：复用已有合同，明确生产者与消费者

写任务前检查实际符号。已有 `PostCCObservationFactV1` 或 `PostCCJointReplaySampleV1` 时，新任务通常是存储、严格验证、materializer 或 adapter，不是再定义一个同名不同义类。

跨组件字段要追踪到 consumer 的算法含义：

- `sampling_probability_or_weight` 必须说明是选择概率还是 loss 权重、取值域、如何应用；不得让 learner 猜。
- bootstrap ref 必须指向可恢复的真实后继与边界，而不是一段无法解析的字符串。
- hash 的覆盖字段、codec、数值精度与校验顺序必须一致；不能一边要求精确 content hash，一边容许任意数值重写还沿用旧 hash。
- 名义联合动作与真实 behavior `log_mu` 保留；损坏、缺失、跨身份配对必须可检测。

资格证明的是持久事实可独立恢复训练真值，不是禁止任何内存缓存。经校验的 durable 数据进入 batch/缓存是正常计算；collector 私有记录成为无法重建的唯一训练来源才是要排除的路径。

## 10. SW-09：依赖按产物组织，不能只按章节号顺排

数学 oracle、具体 task 设计与数据平面的部分实现可以独立推进；依赖未来产物的任务要明确等待哪一个出口。

判定逻辑须在读取正式科学结果之前实现、固定并通过预构造的 PASS/FAIL/边界记录检查。若“gate compiler”编号在 runner 之后，区分“先实现并冻结判定器”与“运行后汇总并签发 receipt”两个时点；不必重编全套任务号。

不是所有测试都需全量重跑。优先验证实际变更的合同和风险，保留要求的资格集合；不能用增加形式检查替代核心科学检查。

## 11. SW-10：预算应覆盖整个训练过程

至少区分 policy decisions、机械 environment advances、replay sample 消费、optimizer updates、evaluation decisions、controls 与重试。采集上限不会自动限制反复学习次数。

同时给阶段/单任务资源边界：墙钟、CPU/GPU、RAM/VRAM、持久存储与恢复方式。未知吞吐可先做有界工程 canary；不能把旧合成 benchmark 当新 learner 的真实吞吐，也不能以“还有预算”无上限重试失败种子。

种子分角色：初始化、环境、动作、replay、评价。若初始化 checkpoint 已固定 hash，五个 seed 不自动代表五份独立初始化；如实说明重复覆盖的是哪些随机性，不能破坏初始身份。

## 12. SW-11：进度和证据分别报告

有效进度是可消费的净产物及通过的验收，可能是代码、解析验证、必要的具体 spec 或结果；不是 commit 次数、模块数或重复重述缺口。

不要要求“每个会话必须有代码 commit”来替代任务判断：审阅、合同修订和真正的科学 FAIL 也可能是有效工作。但执行任务已明确且授权时，不能只发现“还没实现”就停止。

交接固定格式：实际 head、已完成的 task/产物、实际检查、最早未完成项、具体下一动作、如有阻塞则给可复现原因。不能把 `baseline written` 宣称成 durable replay 或 learnability 已实现。

## 13. SW-12：文档维护也要保护冻结身份

新角色原则或审阅结论不能静默覆盖已冻结科学参数、数据权限或历史证据。引用精确版本；需要的后继补充单独发布。只改导航状态时保留原任务作为历史要求，不重开已经合格的阶段。

## 14. SW-13：把 Shanxi CI 写进任务，不用临时沙盒替代

每个涉及运行的任务必须说明：GitHub Actions workflow/待实现入口、共享 preflight 依赖、Shanxi Docker runner、verified canonical Python、实际测试范围、资源预算及结果位置。冒烟、专项运行和正式资格经该路径执行；临时沙盒只做阅读、编辑和静态准备，不运行业务测试或推断远端结论。

当前 Main Smoke 只有手动触发且只覆盖旧 Stage-4 测试，不能替 S1 新行为背书。按 [三层协议第 3 节](ROLES_AND_REVIEW_PROTOCOL.md) 核对实际 SHA、运行步骤、测试数量/结果与 artifact。没有覆盖就安排 CI 实现；等待 runner 不等于允许改用临时环境签发 PASS。纯说明性文档维护遵守该节的静态检查边界。

用户审核 Astra 的文档；Astra 审核 Sol 的 TODO；Sol 审核 DS Flash 的代码。模型换代、赶进度或 commit 数量都不改变这条责任链。
